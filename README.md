## 📖 1. 프로젝트 소개 & 핵심 목표

### 프로젝트 소개
마비노기의 제작 시스템은 하나의 아이템을 만들기 위해 여러 단계의 재료가 필요하고, 각 재료마다 **경매장 구매, 구슬 교환, NPC 구매, 직접 제작** 등 다양한 획득 방법이 존재합니다.  
**LOREWAY TOOLKIT**은 보유 재료와 현재 경매장 시세를 반영해 더 효율적인 제작 경로를 찾을 수 있도록 만든 C# WPF 기반 Windows 데스크톱 애플리케이션입니다.

### 핵심 목표
> **복잡한 제작 과정과 획득 방법을 직접 비교·계산하는 불편을 줄이고, 보유 재료와 시세를 반영한 제작 판단을 돕습니다.**

## ✨ 3. 핵심 기능 4선 (Core Features)

| 번호 | 핵심 기능 | 세부 설명 |
| :---: | :--- | :--- |
| **01** | **다단계 제작 트리** | 제작 대상부터 1차 가공품, 하위 원자재까지 들여쓰기 기반 계층형 트리뷰(`TreeView`)로 한눈에 확인하며, 각 단계별 최적 조달 방법 및 필요/보유/부족 수량을 직관적으로 확인 |
| **02** | **제작 비용 최적화** | 경매장 최저가, 구슬 교환, NPC 상점 구매, 직접 제작 등 모든 경로의 단가를 실시간 비교하여 가장 비용이 적게 드는 최적 루트 및 예상 절감액 산출 |

| **04** | **필요 재료 정리** | 다단계 최적화 경로의 최종 단계에서 사용자가 실제로 경매장이나 상점에서 확보해야 할 순수 원자재(Leaf Nodes)만 별도 탭에 체크리스트 형태로 정리 제공 |

## 🛠️ 4. 주요 기술 구현 포인트 (Technical Highlights)

### 1) 재귀 제작 비용 계산 (Recursive Optimization Engine)
- 하위 레시피를 깊이 우선(DFS) 방식으로 재귀 탐색하면서 각 단계에서 가장 비용이 낮은 획득 방법(`Min(Auction, Orb, Npc, Craft, Ducat)`)을 동적으로 선택합니다.
- 하위 재료들의 최적 비용 합산 결과를 상위 단계의 '직접 제작 비용'으로 실시간 반영하는 상향식(Bottom-up) 동적 의사결정 알고리즘을 적용했습니다.

### 2) NEXON Open API 연동 및 2-Tier 캐싱
- 필요 재료의 경매장 최저가를 비동기(`async/await`)로 신속하게 조회합니다.
- 동일 아이템 중복 조회를 방지하고 넥슨 API 분당 호출 한도(Rate Limit)를 준수하기 위해 **10분 TTL 인메모리 캐시**와 **로컬 JSON 영구 캐시(`auction-cache.json`)**를 2단계로 결합하여 네트워크 부하를 최소화했습니다.
- 동일 아이템에 대한 동시 요청 시 중복 HTTP 패킷을 보내지 않는 **In-Flight Task 공유 패턴**을 적용했습니다.

### 3) 데이터 구조 분리 (Data Separation)
- `Recipe`(제작 배합표), `Inventory`(보유 재료 수량), `AcquisitionMethod`(조달 경로 및 고정 상점/구슬 시세)를 역할별로 엄격히 분리했습니다.
- 동일한 아이템이 어떤 레시피에서는 최종 제작 대상이면서 다른 레시피에서는 하위 가공 재료로 쓰이는 경우에도 데이터 왜곡 없이 일관되게 관리됩니다.

## 🚀 10. 빠른 실행 가이드 (Quick Start)

### Option A. 무설치 단일 실행 파일 실행 (가장 추천 ⭐)
1. 바탕화면의 `LorewayToolkit1` 폴더(또는 배포 패키지)로 이동합니다.
2. **`LorewayToolkit.exe`**를 더블 클릭합니다.  
   *(.NET 런타임이 없어도 단독 실행되며, 오프라인 시세 캐시가 내장되어 있어 API Key가 없어도 모든 기능을 100% 체험할 수 있습니다.)*
3. 실시간 최신 경매장 시세를 직접 연동하고 싶다면 `.env.example`의 이름을 `.env`로 바꾸고 본인의 넥슨 API Key를 입력합니다.

### Option B. 개발 소스 코드 빌드 및 실행 (.NET 8 SDK 환경)
```powershell
# 1. 저장소 클론
git clone https://github.com/PhorinKid/LorewayToolkit.git
cd LorewayToolkit

# 2. .env 키 설정 (선택 사항)
cp .env.example .env

# 3. 빌드 및 실행
dotnet build
dotnet run
```

## 💬 11. 기술 면접 대비 Q&A (핵심 16선)

<details>
<summary><b>Q1. 왜 C#과 WPF를 선택했는가?</b></summary>
<br>
마비노기 이용자들은 PC 환경에서 게임 클라이언트와 계산 도구를 동시에 띄워두고 플레이하는 전형적인 데스크톱 유저입니다. C# .NET 8과 WPF는 Windows 네이티브 환경에서 반응성이 매우 뛰어나며, 강력한 XAML 데이터 바인딩과 MVVM 패턴을 지원하여 다단계 계층형 트리와 실시간 인라인 편집 UI를 가장 유려하고 안정적으로 렌더링할 수 있어 채택했습니다.
</details>

<details>
<summary><b>Q2. MVVM 패턴을 적용한 이유와 View-Service 분리의 이점은?</b></summary>
<br>
WPF의 핵심인 데이터 바인딩을 극대화하고 UI와 비즈니스 로직의 결합도를 낮추기 위함입니다. View는 순수 XAML UI 표시와 커맨드 바인딩만 담당하고, 계산이나 API 통신은 ViewModel과 Service로 완벽히 격리함으로써 단위 테스트가 쉬워지고 UI 스타일을 전면 수정하더라도 핵심 알고리즘 엔진에 아무런 영향이 없습니다.
</details>

<details>
<summary><b>Q3. 왜 DB 대신 JSON 파일 영속화를 채택했는가?</b></summary>
<br>
본 프로그램은 단일 클라이언트용 경량 데스크톱 도구입니다. 관리하는 데이터(레시피 수십 종, 시세 캐시, 보유량)의 규모가 수백 KB 수준으로 매우 가볍기 때문에, 무거운 RDBMS 라이브러리를 종속성으로 추가하기보다 `System.Text.Json`을 이용한 파일 기반 관리가 배포 바이너리 용량과 초기 구동 속도 면에서 훨씬 가볍고 이식성이 뛰어났기 때문입니다.
</details>

<details>
<summary><b>Q4. 10분 시세 캐시 정책을 구현한 이유와 동작 방식은?</b></summary>
<br>
경매장 시세는 초 단위로 급변하지 않으며, NEXON Open API의 분당 호출 제한(Rate Limit)을 엄격히 준수해야 합니다. 10분 TTL 인메모리 캐시를 적용하여 탭 전환이나 보유량 수정 시 API 호출을 0회로 유지합니다. 10분 미만 데이터는 캐시를 즉시 반환하고, 만료되었거나 신규 아이템만 선별 조회합니다.
</details>

<details>
<summary><b>Q5. 일반 갱신과 강제 갱신의 차이는 무엇인가?</b></summary>
<br>
일반 갱신은 10분 TTL 정책을 준수하여 만료된 아이템만 선별적으로 API를 호출하므로 네트워크 트래픽을 최소화합니다. 반면 강제 갱신은 사용자가 시장 변동을 즉각 재확인하고 싶을 때 10분 TTL을 무시하고 현재 필요한 모든 재료의 최신 시세를 강제로 다시 조회합니다.
</details>

<details>
<summary><b>Q6. 동일 아이템 API 중복 요청을 어떻게 방지했는가?</b></summary>
<br>
첫째, 트리 탐색 과정에서 필요한 모든 아이템을 `HashSet<string>`으로 수집하여 중복을 1차 제거했습니다. 둘째, 비동기 호출 시점에 `ConcurrentDictionary`를 활용한 In-Flight Task 공유 패턴을 적용하여, 동일 아이템에 대한 비동기 작업이 이미 진행 중인 경우 새 HTTP 요청을 만들지 않고 기존 Task 결과를 공유받도록 구현했습니다.
</details>

<details>
<summary><b>Q7. 다단계 재귀 제작 비용 계산 엔진의 동작 방식은?</b></summary>
<br>
상위 재료에서 필요한 부족 수량을 기준으로, 해당 재료를 조달할 수 있는 모든 방법(경매장, 구슬, NPC, 제작 등)을 평가합니다. '제작'의 경우 해당 하위 레시피 재료들을 다시 `OptimizeItemCost()`로 재귀 호출하여 각 하위 재료의 최소 비용을 구한 뒤 합산합니다. 최종적으로 하위 제작 총비용과 직접 완제품 구매 비용 중 최소값을 선택하는 상향식(Bottom-up) 동적 최적화 방식으로 동작합니다.
</details>

<details>
<summary><b>Q8. 순환 레시피(A→B→A)는 어떻게 감지하고 차단했는가?</b></summary>
<br>
사용자가 새 레시피를 등록할 때 깊이 우선 탐색(DFS) 기반의 사이클 감지(`CheckCycle`) 알고리즘을 실행합니다. 현재 탐색 경로를 `visitedPath` 집합으로 추적하여, 하위 재료를 탐색하다가 이미 경로에 존재하는 아이템을 다시 참조할 경우 저장을 차단하고 구체적인 순환 경로(예: `A -> B -> A`)를 사용자에게 에러 메시지로 안내합니다.
</details>

<details>
<summary><b>Q9. 보유 재료가 하위 레시피 계산에 어떻게 반영되는가?</b></summary>
<br>
최적화 시작 시 전역 인벤토리 사본을 생성합니다. 특정 레시피 노드를 평가할 때 `부족 수량 = Max(필요 수량 - 보유 수량, 0)`을 계산하고 사용된 수량만큼 작업 인벤토리에서 차감합니다. 만약 상위 재료 10개 중 3개를 보유하고 있다면 부족 수량인 7개에 대해서만 하위 레시피 제작을 재귀 호출하므로, 불필요한 하위 재료 비용이 과다 계산되지 않습니다.
</details>

<details>
<summary><b>Q10. 가격 정보가 없을 때 왜 0원으로 처리하면 안 되는가?</b></summary>
<br>
경매장 매물이 없거나 API 조회가 실패했을 때 0원으로 처리하면 최적화 알고리즘이 해당 재료를 "비용이 들지 않는 가장 좋은 획득 경로"로 오판하여 사용자에게 잘못된 제작 추천을 제공하게 됩니다. 따라서 가격이 없는 항목은 `IsFeasible = false` 및 `시세 미확인` 상태로 분리하여 최적화 결과에서 배제하고 사용자에게 시세 확인이 필요함을 명시합니다.
</details>

<details>
<summary><b>Q11. API 호출 실패 시 기존 캐시를 어떻게 보호하는가?</b></summary>
<br>
일시적인 네트워크 단절이나 넥슨 서버 점검으로 인해 갱신이 실패하더라도 기존 캐시 엔트리가 존재한다면 절대 삭제하거나 0원으로 덮어쓰지 않습니다. 기존 시세를 그대로 유지한 채 `새로고침 실패 (이전 시세 유지됨)` 안내를 제공하여 사용자의 기존 작업 흐름이 끊기지 않도록 방어적으로 설계했습니다.
</details>

<details>
<summary><b>Q12. Recipe와 AcquisitionMethod 도메인을 분리한 이유는?</b></summary>
<br>
'제작 레시피(어떤 재료 몇 개로 무엇을 만드는가)'와 '획득 방법(경매장 매물, 구슬 교환, NPC 상점 등)'은 도메인의 책임이 다릅니다. 레시피는 순수 제작 배합표이며, 획득 방법은 게임 시스템 및 시장 환경에 따라 추가되거나 수정될 수 있습니다. 두 도메인을 분리함으로써 새로운 획득처가 추가되더라도 기존 제작 레시피 스키마를 훼손하지 않는 OCP(개방-폐쇄 원칙)를 달성했습니다.
</details>

<details>
<summary><b>Q13. async / await 비동기 처리를 전면 적용한 이유는?</b></summary>
<br>
NEXON Open API는 외부 HTTP 통신으로 수백 밀리초의 지연이 발생할 수 있습니다. 이를 동기식으로 호출하면 Windows 메시지 루프가 블로킹되어 UI가 멈추거나 응답 없음(Not Responding) 현상이 발생합니다. `HttpClient`의 비동기 메서드와 `async/await`를 사용하여 백그라운드 I/O 작업 중에도 UI 렌더링과 사용자 조작이 매끄럽게 유지되도록 구현했습니다.
</details>

<details>
<summary><b>Q14. API Key를 코드에 하드코딩하지 않은 이유는?</b></summary>
<br>
개인 API Key가 GitHub 등 공개 저장소에 노출될 경우 키 도용으로 인한 호출 한도 소진이나 보안 사고가 발생할 수 있습니다. `.env` 파일과 시스템 환경변수에서 동적으로 로드하도록 분리하고, `.gitignore`로 형상 관리에서 제외하여 배포 바이너리와 저장소의 보안 무결성을 보장했습니다.
</details>

<details>
<summary><b>Q15. AI가 제안한 코드를 어떻게 신뢰하고 검증했는가?</b></summary>
<br>
AI가 생성한 알고리즘과 코드를 무조건 수용하지 않고, 세 단계로 철저히 검증했습니다. 첫째, NEXON 공식 API 문서와 C# 표준 명세를 대조하여 문법과 파라미터를 확인했습니다. 둘째, 대표 레시피(`찬란한 기억의 결정`)에 대해 사람이 직접 손계산한 정답 시나리오를 구성하고, 프로그램의 실제 실행 결과와 비교하는 단위 검증 스크립트를 실행하여 100% 일치함을 입증했습니다. 셋째, 정적 코드 분석과 빌드 무결성 검사를 통해 잠재적 오류를 제거했습니다.
</details>

<details>
<summary><b>Q16. 향후 이 프로젝트를 웹 서비스로 확장한다면 어떻게 설계할 것인가?</b></summary>
<br>
현재 데스크톱 클라이언트가 직접 NEXON API를 호출하는 구조에서, 중앙 백엔드(예: ASP.NET Core) 서버를 프록시로 구축할 것입니다. 백엔드에서 Redis 캐시를 통해 전체 유저의 시세 요청을 통합 캐싱하면 NEXON API 호출량을 99% 이상 절감할 수 있으며, 클라이언트는 가벼운 웹 프론트엔드나 모바일 앱으로도 동일한 최적화 기능을 이용할 수 있게 확장할 수 있습니다.
</details>
