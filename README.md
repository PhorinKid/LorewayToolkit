## 📌 1. 프로젝트 기획 및 배경

### 1.1 해결하고자 한 문제
마비노기의 상위 종결 장비(예: *소울 리버레이트 보우*, *나이트브링어* 등) 제작은 복잡한 다단계 하위 레시피와 방대한 수량의 재료를 요구합니다.
- **다양한 조달 경로의 혼재**: 동일한 재료라도 ① 경매장 구매, ② 던전 보상 구슬 교환, ③ NPC 상점 골드 구매, ④ 하위 재료 직접 제작 등 획득 경로가 나뉩니다.
- **실시간 시세 변동의 한계**: 경매장 매물 가격이 실시간으로 변동하여 "완제품을 바로 사는 것", "재료를 사서 만드는 것", "구슬로 바꾸는 것" 중 무엇이 가장 저렴한지 손계산하기가 극도로 어렵습니다.
- **인벤토리 보유량에 따른 연쇄 계산**: 플레이어가 이미 일부 중간 재료를 보유하고 있을 경우, 필요한 하위 레시피 수량이 동적으로 변동하여 연쇄 계산이 필수적입니다.

### 1.2 솔루션
**NEXON Open API**를 연동하여 실시간 최저가를 조회하고, **다단계 재귀 비용 최적화 엔진**을 통해 모든 획득 경로의 실시간 가치를 비교하여 **최소 제작 비용 및 최적 획득 조합**을 1초 이내에 사용자에게 시각적으로 제안합니다.

## 🛠️ 3. 기술 스택 및 시스템 아키텍처

### 3.1 기술 스택
- **Language**: C# 12.0 (.NET 8.0)
- **UI Framework**: Windows Presentation Foundation (WPF, XAML)
- **Architecture**: MVVM (Model-View-ViewModel) + Service Layer
- **Network**: `HttpClient`, `async/await` 비동기 논블로킹 I/O
- **Serialization**: `System.Text.Json` (초경량 고성능 파일 영속화)

## 🧠 4. 핵심 알고리즘: 다단계 재귀 비용 최적화 엔진

### 4.1 알고리즘 로직 흐름
```text
[최적화 탐색 알고리즘 흐름]
1. 보유량(Inventory) 우선 차감:
   부족 수량(Missing) = Max(필요 수량 - 보유 수량, 0)
   -> 부족 수량이 0이면 비용 0 G (방법: "보유 재료") 반환

2. 각 획득 경로별 비용 평가:
   ├── A. 경매장(Auction) : 부족 수량 × 경매장 최저가
   ├── B. 구슬(Orb)       : 부족 수량 × 필요 구슬 수 × 구슬당 Gold 가치
   ├── C. NPC 상점        : 부족 수량 × 상점 고정 판매가
   ├── D. 두카트(Ducat)   : 두카트 상점 획득 가능 여부 확인
   └── E. 직접 제작(Craft):
          하위 레시피 탐색 -> 각 하위 재료에 대해 OptimizeItemCost() 재귀 호출
          하위 제작 총비용 = ∑(하위 재료별 최소 비용)

3. 최적 경로 채택:
   Min(Auction, Orb, Npc, Craft, Ducat) 중 가장 저렴한 경로를 선정하여 부모 노드로 반환
```

### 4.2 실제 계산 검증 (손계산 vs 프로그램 엔진 100% 일치)
대표 다단계 복합 레시피인 **`찬란한 기억의 결정`**을 기준으로 사람의 수작업 검증값과 엔진 결과를 비교 검증했습니다.

| 재료명 | 필요 | 보유 | 부족 | 선택된 획득처 | 손계산 예상 비용 | 프로그램 산출 비용 | 일치 여부 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **주황빛 기억의 조각** | 3개 | 1개 | 2개 | **구슬 (Orb)** | 17,500,000 G | 17,500,000 G | ✅ 100% PASS |
| **아라고나이트** | 10개 | 0개 | 10개 | **경매장 (Auction)** | 8,000,000 G | 8,000,000 G | ✅ 100% PASS |
| **마력이 깃든 융합제** | 5개 | 0개 | 5개 | **NPC 상점 (Npc)** | 2,500,000 G | 2,500,000 G | ✅ 100% PASS |
| **퓨어 젬스톤** | 2개 | 0개 | 2개 | **직접 제작 (Craft)** | 3,280,000 G | 3,280,000 G | ✅ 100% PASS |
| **총 제작 비용** | - | - | - | **최종 최소 비용** | **31,280,000 G** | **31,280,000 G** | **✅ 100% PASS** |

## ⚡ 5. 네트워크 및 캐싱 최적화 (API Rate Limit 대응)

1. **10분 TTL 2-Tier 캐싱**:
   - **In-Memory**: 최근 10분 이내 조회된 가격은 메모리 캐시를 재사용하여 탭 전환이나 노드 클릭 시 API 호출 **0회** 유지.
   - **Persistent File (`auction-cache.json`)**: 조회된 시세 및 사용자 수동 입력가를 로컬에 영구 보존하여 프로그램 재실행 시 즉시 복원.
2. **In-Flight Task 동시성 제어**:
   - 동일 아이템에 대한 비동기 요청이 진행 중일 때, 중복 HTTP 요청을 보내지 않고 `ConcurrentDictionary<string, Task<AuctionFetchResult>>`에 등록된 기존 Task의 결과를 공유받아 대기합니다.
3. **Unique Items Set 일괄 수집**:
   - 트리 내에 동일한 재료가 여러 레시피에서 수십 번 중복 등장하더라도, 갱신 전 `HashSet<string>`으로 추출하여 단 1번만 요청합니다.
4. **오프라인/장애 내구성 (Graceful Degradation)**:
   - 네트워크 연결이 끊기거나 API 키가 없는 경우에도 앱이 크래시되지 않고 로컬 캐시 데이터를 기반으로 모든 제작 계산이 정상 동작합니다.

## 🔒 6. 보안 및 Secret 관리 정책

- **개인 API Key 하드코딩 배제**: 소스 코드(C#, XAML, JSON 등) 어디에도 개인 API Key를 기록하지 않습니다.
- **동적 로드 우선순위**:
  1. 실행 파일 경로 및 프로젝트 루트의 `.env` 파일 (`NEXON_API_KEY=...`)
  2. 시스템 OS 환경변수 (`NEXON_API_KEY`)
- **Git & 배포 보안**:
  - `.gitignore`에 `.env`, `bin/`, `obj/` 등을 포함하여 Git 저장소에 키가 커밋되는 것을 원천 차단했습니다.
  - 배포 패키지에는 실제 키를 제거하고 형식 안내용 **`.env.example`** 파일만 동봉합니다.

## 🤖 7. AI 페어 프로그래밍 협업 및 주도적 검증

본 프로젝트는 최신 AI 코딩 어시스턴트를 단순 복사-붙여넣기 도구가 아닌 **엔지니어링 파트너**로 적극 활용하여 개발 효율과 품질을 극대화했습니다.

```text
[개발자 (주도적 설계 및 검증)]               [AI 어시스턴트 (구현 및 분석 지원)]
 1. 요구사항 정의 & 게임 도메인 분석 ────▶  초기 보일러플레이트 코드 제안
 2. MVVM 아키텍처 및 Service 구조 확립 ─▶  Service / ViewModel 분리 구현 지원
 3. 에지 케이스 규명 (순환참조, 연쇄차감) ─▶  DFS 사이클 감지 알고리즘 초안 도출
 4. 손계산 기반 알고리즘 무결성 교차 검증 ◀── 단위 테스트 스크립트 작성 및 대조
 5. 코드 리뷰, 불필요 코드 정리, 최적화 ──▶  Self-Contained 빌드 스크립트 구성
```

- **도메인 특화 비즈니스 룰 정의**: 마비노기의 특수한 '구슬 교환', '상위 재료 보유 시 하위 재료 수량 연쇄 차감' 규칙을 명확한 수학적 제약조건으로 정립하여 AI에게 프롬프팅.
- **엄격한 결과물 검증 (Human-in-the-Loop)**: AI가 작성한 계산 로직을 맹신하지 않고, 실제 손계산 검증표(Verification Table)를 작성하여 100% 일치하는지 단위 스크립트로 교차 검증.
- **코드 리팩토링 및 클린 코드 유지**: 방대한 주석과 불필요한 보일러플레이트를 정리하고, WPF 렌더링 병목(파란색 선택 테두리, 레이아웃 정렬 등)을 주도적으로 개선.

## ⚠️ 8. 현재의 한계 및 향후 개선 로드맵

솔직한 엔지니어링 관점에서 파악한 본 프로젝트의 한계점과 실무 수준으로 도약하기 위한 개선 과제입니다.

### 8.1 현재의 한계 (Current Limitations)
1. **정적 데이터의 로컬 관리 한계**:
   - NEXON Open API가 현재 경매장 외에 'NPC 상점 판매 목록'이나 '던전 보상 구슬 교환비' API를 제공하지 않아, 이 정보는 로컬 JSON(`acquisition-methods.json`)으로 수동 관리해야 합니다.
2. **단일 클라이언트의 API 호출 한계**:
   - 각 클라이언트가 개별적으로 API를 호출하므로, 사용자가 많아질 경우 개인 API Key의 분당 호출 한도(Rate Limit)에 도달할 위험이 있습니다.
3. **단일 서버(류트) 중심 시세**:
   - 현재 기준 가장 매물이 풍부한 류트 서버를 우선으로 연동되어 있어 타 서버 이용자를 위한 멀티 서버 옵션이 미비합니다.

### 8.2 향후 개선 과제 (Roadmap)
- [ ] **백엔드 프록시 캐싱 서버 구축 (ASP.NET Core / Redis)**:
  - 개별 클라이언트가 직접 넥슨 API를 호출하지 않고 중앙 백엔드를 거치도록 전환. Redis를 통해 전 유저가 시세를 공유하면 API 호출량을 99% 이상 절감 가능.
- [ ] **시세 변동 추이 차트 (LiveCharts / OxyPlot)**:
  - 최근 7일간의 가격 변동 추이와 거래량을 그래프로 시각화하여 "지금 제작하는 것이 이득인가"를 예측해 주는 지표 제공.
- [ ] **웹 / 크로스 플랫폼 확장 (Blazor / Avalonia)**:
  - Windows에 종속된 WPF 환경을 넘어 모바일과 웹 브라우저에서도 접근할 수 있도록 UI 프레임워크 확장.

## 💬 10. 기술 면접 Q&A (핵심 기술 질문 16선)

<details>
<summary><b>Q1. 왜 C#과 WPF를 선택했는가?</b></summary>
<br>
마비노기 유저들은 PC 환경에서 게임과 보조 도구를 동시에 띄워두고 멀티태스킹하는 데스크탑 사용자층입니다. C# .NET 8과 WPF는 Windows 네이티브 환경에서 반응성이 매우 뛰어나고, 강력한 XAML 데이터 바인딩과 MVVM 패턴을 지원하여 복잡한 계층형 제작 트리와 인라인 데이터 편집 UI를 가장 유려하고 안정적으로 렌더링할 수 있어 채택했습니다.
</details>

<details>
<summary><b>Q2. MVVM 패턴을 적용한 이유와 View-Service 분리의 이점은?</b></summary>
<br>
WPF의 핵심인 데이터 바인딩을 극대화하고 UI와 비즈니스 로직의 결합도를 낮추기 위함입니다. View는 순수 XAML UI 표시와 커맨드 바인딩만 담당하고, 계산이나 API 통신은 ViewModel과 Service로 완벽히 격리함으로써 단위 테스트가 쉬워지고 UI 스타일을 전면 수정하더라도 핵심 알고리즘 엔진에 아무런 영향이 없습니다.
</details>

<details>
<summary><b>Q3. 왜 DB(SQLite 등) 대신 JSON 파일 영속화를 채택했는가?</b></summary>
<br>
본 프로그램은 단일 클라이언트용 경량 데스크탑 도구입니다. 관리하는 데이터(레시피 수십 종, 시세 캐시, 보유량)의 규모가 수백 KB 수준으로 매우 가볍기 때문에, 무거운 RDBMS 라이브러리를 종속성으로 추가하기보다 `System.Text.Json`을 이용한 파일 기반 관리가 배포 바이너리 용량과 초기 구동 속도 면에서 훨씬 가볍고 이식성이 뛰어났기 때문입니다.
</details>

<details>
<summary><b>Q4. 10분 시세 캐시 정책을 구현한 이유와 동작 방식은?</b></summary>
<br>
경매장 시세는 초 단위로 급변하지 않으며, NEXON Open API의 분당 호출 제한(Rate Limit)을 엄격히 준수해야 합니다. 10분 TTL 인메모리 캐시를 적용하여 탭 전환이나 보유량 수정 시 API 호출을 0회로 유지합니다. 10분 미만 데이터는 캐시를 즉시 반환하고, 만료되었거나 신규 아이템만 선별 조회합니다.
</details>

<details>
<summary><b>Q5. 일반 갱신과 강제 갱신의 차이는 무엇인가?</b></summary>
<br>
일반 갱신은 10분 TTL 정책을 준수하여 만료된 아이템만 선별적으로 API를 호출하므로 네트워크 트래픽을 최소화합니다. 반면 강제 갱신은 사용자가 시장 변동을 즉각 재확인하고 싶을 때 10분 TTL을 무시하고 현재 필요한 모든 재료의 최신 시세를 강제로 다시 조회합니다.
</details>

<details>
<summary><b>Q6. 동일 아이템 API 중복 요청을 어떻게 방지했는가?</b></summary>
<br>
첫째, 트리 탐색 과정에서 필요한 모든 아이템을 `HashSet<string>`으로 수집하여 중복을 1차 제거했습니다. 둘째, 비동기 호출 시점에 `ConcurrentDictionary`를 활용한 In-Flight Task 공유 패턴을 적용하여, 동일 아이템에 대한 비동기 작업이 이미 진행 중인 경우 새 HTTP 요청을 만들지 않고 기존 Task 결과를 공유받도록 구현했습니다.
</details>

<details>
<summary><b>Q7. 다단계 재귀 제작 비용 계산 엔진의 동작 방식은?</b></summary>
<br>
상위 재료에서 필요한 부족 수량을 기준으로, 해당 재료를 조달할 수 있는 모든 방법(경매장, 구슬, NPC, 제작 등)을 평가합니다. '제작'의 경우 해당 하위 레시피 재료들을 다시 `OptimizeItemCost()`로 재귀 호출하여 각 하위 재료의 최소 비용을 구한 뒤 합산합니다. 최종적으로 하위 제작 총비용과 직접 완제품 구매 비용 중 최소값을 선택하는 상향식(Bottom-up) 동적 최적화 방식으로 동작합니다.
</details>

<details>
<summary><b>Q8. 순환 레시피(A→B→A)는 어떻게 감지하고 차단했는가?</b></summary>
<br>
사용자가 새 레시피를 등록할 때 깊이 우선 탐색(DFS) 기반의 사이클 감지(`CheckCycle`) 알고리즘을 실행합니다. 현재 탐색 경로를 `visitedPath` 집합으로 추적하여, 하위 재료를 탐색하다가 이미 경로에 존재하는 아이템을 다시 참조할 경우 저장을 차단하고 구체적인 순환 경로(예: `A -> B -> A`)를 사용자에게 에러 메시지로 안내합니다.
</details>

<details>
<summary><b>Q9. 보유 재료가 하위 레시피 계산에 어떻게 반영되는가?</b></summary>
<br>
최적화 시작 시 전역 인벤토리 사본을 생성합니다. 특정 레시피 노드를 평가할 때 `부족 수량 = Max(필요 수량 - 보유 수량, 0)`을 계산하고 사용된 수량만큼 작업 인벤토리에서 차감합니다. 만약 상위 재료 10개 중 3개를 보유하고 있다면 부족 수량인 7개에 대해서만 하위 레시피 제작을 재귀 호출하므로, 불필요한 하위 재료 비용이 과다 계산되지 않습니다.
</details>

<details>
<summary><b>Q10. 가격 정보가 없을 때 왜 0원으로 처리하면 안 되는가?</b></summary>
<br>
경매장 매물이 없거나 API 조회가 실패했을 때 0원으로 처리하면 최적화 알고리즘이 해당 재료를 "비용이 들지 않는 가장 좋은 획득 경로"로 오판하여 사용자에게 잘못된 제작 추천을 제공하게 됩니다. 따라서 가격이 없는 항목은 `IsFeasible = false` 및 `시세 미확인` 상태로 분리하여 최적화 결과에서 배제하고 사용자에게 시세 확인이 필요함을 명시합니다.
</details>

<details>
<summary><b>Q11. API 호출 실패 시 기존 캐시를 어떻게 보호하는가?</b></summary>
<br>
일시적인 네트워크 단절이나 넥슨 서버 점검으로 인해 갱신이 실패하더라도 기존 캐시 엔트리가 존재한다면 절대 삭제하거나 0원으로 덮어쓰지 않습니다. 기존 시세를 그대로 유지한 채 `새로고침 실패 (이전 시세 유지됨)` 메시지를 제공하여 사용자의 기존 작업 흐름이 끊기지 않도록 방어적으로 설계했습니다.
</details>

<details>
<summary><b>Q12. Recipe와 AcquisitionMethod 도메인을 분리한 이유는?</b></summary>
<br>
'제작 레시피(어떤 재료 몇 개로 무엇을 만드는가)'와 '획득 방법(경매장 매물, 구슬 교환, NPC 상점 등)'은 도메인의 책임이 다릅니다. 레시피는 순수 제작 배합표이며, 획득 방법은 게임 시스템 및 시장 환경에 따라 추가되거나 수정될 수 있습니다. 두 도메인을 분리함으로써 새로운 획득처가 추가되더라도 기존 제작 레시피 스키마를 훼손하지 않는 OCP(개방-폐쇄 원칙)를 달성했습니다.
</details>

<details>
<summary><b>Q13. async / await 비동기 처리를 전면 적용한 이유는?</b></summary>
<br>
NEXON Open API는 외부 HTTP 통신으로 수백 밀리초의 지연이 발생할 수 있습니다. 이를 동기식으로 호출하면 Windows 메시지 루프가 블로킹되어 UI가 멈추거나 응답 없음(Not Responding) 현상이 발생합니다. `HttpClient`의 비동기 메서드와 `async/await`를 사용하여 백그라운드 I/O 작업 중에도 UI 렌더링과 사용자 조작이 매끄럽게 유지되도록 구현했습니다.
</details>

<details>
<summary><b>Q14. API Key를 코드에 하드코딩하지 않은 이유는?</b></summary>
<br>
개인 API Key가 GitHub 등 공개 저장소에 노출될 경우 키 도용으로 인한 호출 한도 소진이나 보안 사고가 발생할 수 있습니다. `.env` 파일과 시스템 환경변수에서 동적으로 로드하도록 분리하고, `.gitignore`로 형상 관리에서 제외하여 배포 바이너리와 저장소의 보안 무결성을 보장했습니다.
</details>

<details>
<summary><b>Q15. AI가 제안한 코드를 어떻게 신뢰하고 검증했는가?</b></summary>
<br>
AI가 생성한 알고리즘과 코드를 무조건 수용하지 않고, 세 단계로 철저히 검증했습니다. 첫째, NEXON 공식 API 문서와 C# 표준 명세를 대조하여 문법과 파라미터를 확인했습니다. 둘째, 대표 레시피(`찬란한 기억의 결정`)에 대해 사람이 직접 손계산한 정답 시나리오를 구성하고, 프로그램의 실제 실행 결과와 비교하는 단위 검증 스크립트를 실행하여 100% 일치함을 입증했습니다. 셋째, 정적 코드 분석과 빌드 무결성 검사를 통해 잠재적 오류를 제거했습니다.
</details>

<details>
<summary><b>Q16. 향후 이 프로젝트를 웹 서비스로 확장한다면 어떻게 설계할 것인가?</b></summary>
<br>
현재 데스크탑 클라이언트가 직접 NEXON API를 호출하는 구조에서, 중앙 백엔드(예: ASP.NET Core) 서버를 프록시로 구축할 것입니다. 백엔드에서 Redis 캐시를 통해 전체 유저의 시세 요청을 통합 캐싱하면 NEXON API 호출량을 99% 이상 절감할 수 있으며, 클라이언트는 가벼운 웹 프론트엔드나 모바일 앱으로도 동일한 최적화 기능을 이용할 수 있게 확장할 수 있습니다.
</details>
